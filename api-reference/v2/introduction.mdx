The Print.App REST API lets your **server** manage your account: create designs at a size and place text, images and shapes on them, organise them in folders, upload graphics and fonts, set up palettes, choose which designs each product opens, and read and manage your customers' projects. It also answers simpler questions, such as whether a project a customer is ordering really belongs to your store.

<Note>
The API is server-to-server. Call it from your backend with a [secret key](/api-reference/v2/authentication), never from browser code. In the browser, the editor runs with your public Domain Key as before.
</Note>

## Base URL

```
https://api.print.app/v2
```

## Authentication

Send a secret key as a bearer token on every request:

```bash
curl https://api.print.app/v2/account \
  -H "Authorization: Bearer sk_…"
```

Create secret keys in the [Print.App admin](https://admin.print.app/api-keys). See [Authentication](/api-reference/v2/authentication).

## Endpoints

| Resource | What you can do |
| --- | --- |
| [Account](/api-reference/v2/account/get) | Read the account a key belongs to. The quickest way to check a key works. |
| [Designs](/api-reference/v2/designs/list) | List, create (blank pages at a trim size, with bleed and safe margin), rename, duplicate and delete designs; add, rename, reorder and remove pages; [read](/api-reference/v2/designs/get-design-content) and [edit](/api-reference/v2/designs/apply-ops) what is on the pages. |
| [Design folders](/api-reference/v2/design-folders/list-design-folders) | Organise designs in folders. |
| [Files](/api-reference/v2/files/list-files) | Upload images and graphics from a URL or straight from your server, then use them in designs. |
| [Graphic folders](/api-reference/v2/graphic-folders/list-graphic-folders) | Choose the graphics your editor offers customers, panel by panel. |
| [Fonts](/api-reference/v2/fonts/list-fonts) | Import Google fonts or upload your own. |
| [Palettes](/api-reference/v2/palettes/list-palettes) | Offer your brand's colours, with CMYK and spot values for print. |
| [Products](/api-reference/v2/products/list-products) | Choose which designs each store product, or variant, opens. |
| [Projects](/api-reference/v2/projects/list) | Read your customers' projects (another account's project answers `404`, so a `200` proves it is yours), add your own details to them, or delete them. |
| [Links](/api-reference/v2/links/create-link) | Make a create.print.app link that opens a design or project in the editor, without a store. |
| [Connectors](/api-reference/v2/connectors/list-connectors) | Make the editor follow the options on your product page: [read the page](/api-reference/v2/connectors/inspect-product-page) for its options and Print Options fields, [test](/api-reference/v2/connectors/test-connector) what each choice will do, then create the connector and [attach it](/api-reference/v2/designs/attach-connector) to designs. |
| [Resource profiles](/api-reference/v2/resource-profiles/list-resource-profiles) | Limit the fonts, palettes and graphic folders the editor offers on some designs. |
| [PDF profiles](/api-reference/v2/pdf-profiles/list-pdf-profiles) | Set how print PDFs are made: colour conversion, PDF standard, cut lines, image resolution and fonts. |
| [3D scenes](/api-reference/v2/3d-scenes/list-scenes) | List your 3D scenes and the library's, and check which suit a design. Set a design's scene with `sceneId` on [Update a design](/api-reference/v2/designs/update-design). |
| [Library](/api-reference/v2/library/list-library-designs) | Find ready-made designs and graphic kits in the Print.App library, by what they are for and the size of your product, and bring them into your account. |
| [Settings](/api-reference/v2/settings/get-settings) | Read and change how the editor opens and behaves, and the selectors Print.App uses on your product pages. A design can set its own over them. |

To check orders against projects, follow [Verify a project before fulfilling](/api-reference/v2/verify-a-project). To build a design from scratch, follow [Create a design through the API](/api-reference/v2/create-a-design).

To be told when a project is created or a file is uploaded rather than asking, use [webhooks](/configuration/webhooks). Turn on [signing](/configuration/webhooks#verify-a-signature) so your server can check that each one comes from Print.App.

## Conventions

- **JSON** request and response bodies, UTF-8, with `camelCase` field names.
- **Every object** carries an `object` field naming its type (`"project"`, `"account"`, `"list"`).
- **Timestamps** are ISO-8601 in UTC, for example `2026-10-17T09:12:03Z`.
- **IDs** keep their prefixes: `dom_…` for your account (your Domain Key), `project_…` for projects, `design_…` for designs.
- **Every response** carries an `x-request-id` header. Quote it when you contact support.
- **Send a `User-Agent` header** that names your integration, for example `User-Agent: MyStore-Integration/1.0`. It isn't required, but it lets us identify your traffic if you need help.
- **Errors** share one shape: see [Errors & rate limits](/api-reference/v2/errors).
- **Lists** are paged with a cursor: see [Pagination](/api-reference/v2/pagination).
- **Writes** take a JSON body (`Content-Type: application/json`). `POST` creates and answers `201`, `PATCH` changes only the fields you send, `PUT` replaces, and `DELETE` answers `{ "object": …, "id": …, "deleted": true }`. Unknown fields are refused, so typos don't go unnoticed.
- **Retries:** send an `Idempotency-Key` header with a `POST`, so retrying it can't create a duplicate. See [Retrying safely](/api-reference/v2/errors#retrying-safely).

## Versioning

The version is in the path (`/v2`). Within v2, changes are additive only: new endpoints, new optional parameters, new fields in responses and new error codes. Write your client to ignore fields it doesn't know.

## OpenAPI spec

The whole API is described in one [OpenAPI 3.1 file](https://print.app/docs/openapi.json): every endpoint, request body, response and design operation. Use it to generate a client, or to check requests before you send them. See [OpenAPI spec](/api-reference/v2/openapi) for what it covers and what to watch for.

<Tip>
The older v1 endpoints that the store plugins use, authenticated with the Auth Key, keep working unchanged. New integrations should use v2.
</Tip>
